## 📌 4.7: "Проектируйте интерфейсы для потомков"

### 📘 Про що цей пункт?
🔑 Головна думка:
>Коли ти створюєш інтерфейс, думай не тільки про сьогоднішню реалізацію, а й про майбутніх реалізаторів (потомків).

>Інтерфейс має бути достатньо загальним, логічним і стабільним, щоб його було легко розширювати без поломок.

### 🛠 Просте пояснення:
Інтерфейс — це обіцянка: "будь-який клас, що його реалізує, буде поводитися ось так (будь-хто, хто мене реалізує, мусить виконати певні умови)".

Якщо інтерфейс спроєктований погано:
- реалізовувати його буде важко або незручно;
- майбутні реалізації будуть погано працювати або ламатись.

Тому, коли проектуєш інтерфейс:
- Уяви, що ти не знаєш, хто і як буде його реалізовувати.
- Зроби так, щоб реалізаторам було зручно і безпечно його імплементувати.
- Не прив'язуйся до конкретної реалізації або особливостей тільки одного класу. 
>Інтерфейси повинні бути мінімальними і стабільними.

❗️ Помилки, яких треба уникати:
- Додавати нові методи в уже існуючий інтерфейс (це ламає всіх реалізаторів).
- Примушувати реалізатора знати забагато про твій внутрішній код.
- Погано обирати рівень абстракції (занадто загальний або занадто конкретний інтерфейс).

### 🧠 Як правильно проектувати інтерфейси для нащадків:
1. Чіткість і мінімалізм
   - Інтерфейс має містити тільки те, що обов’язково потрібно.
2. Без зайвої залежності від реалізації
   - Він не повинен "підштовхувати" до певного способу реалізації.
3. Додавати розширення через нові інтерфейси
   - Коли хочеться додати щось нове — краще створити новий інтерфейс, а не змінювати старий (щоб не ламати існуючі реалізації).
4. Можна додавати default методи, щоб полегшити життя реалізаціям.
- Принцип ISP (Interface Segregation Principle) — маленькі інтерфейси краще.

### 🧠 Висновок:
| *Якщо проектуєш інтерфейс*     | *Пам'ятай*                            |
|--------------------------------|---------------------------------------|
| Він має бути мінімальним       | Можна розширити через нові інтерфейси |
| Не прив'язуй реалізацію        | Надавай свободу для різних реалізацій |
| Можна використовувати default  | Але обережно, не для всього           |



## 4.7 Проектируйте интерфейсы для потомков (Item 21)

В Java 8 у интерфейсов появились дефолтные методы. Но добавление новых методов к существующим интерфейсам сопряжено с
риском. Если добавлять дефолтные методы в существующий интерфейс, то не во всех реализациях интерфейса метод будет
работать корректно.

Не всегда возможно написать дефолтный метод, который поддерживает все инварианты всех мыслимых реализаций.

В присутствии дефолтных методов существующие реализации интерфейсов могут компилироваться без ошибок или предупреждений,
но сбоить во время выполнения.
