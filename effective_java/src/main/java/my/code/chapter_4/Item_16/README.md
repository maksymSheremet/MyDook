## 📌 4.2: "Используйте в открытых классах методы доступа, а не открытые поля"

### 🔑 Головна думка:
> Не робіть поля публічними — навіть якщо це здається зручним. Натомість — використовуйте методи доступу (геттери/сеттери).

### 🛠 Просте пояснення:
Уяви, що ти маєш клас з полем name:

❌ Погано:
```java
public class User {
  public String name;
}
```
Це погано, бо:
- інші частини програми можуть напряму змінювати поле (і поламати логіку);
- неможливо додати перевірки або обмеження;
- неможливо зробити "лінивий підрахунок", кешування чи логування;
- не можна легко змінити реалізацію в майбутньому, бо публічне поле вже використовують напряму.

✅ Добре:
```java
public class User {
  private String name;

  public String getName() {
    return name;
  }

  public void setName(String name) {
    // можна додати перевірку або логіку
    this.name = name;
  }
}
```
>Навіть якщо зараз логіка проста — в майбутньому можна легко її змінити, не ламаючи код користувачів цього класу.

### 🧠 Висновок:
| **Варіант**    | *Добре чи ні?*   | **Чому?** |
|----------------|------------------|-----------|
|public String name;| ❌  | Поле доступне напряму, без контролю |
|private String name + геттер/сеттер| 	✅ |Повна гнучкість і контроль|



## 4.2 Используйте в открытых классах методы доступа, а не открытые поля (Item 16)

Минусы открытых полей:

- Они лишены преимуществ инкапсуляции
- Нельзя изменить представление класса, не изменив его API
- Нельзя обеспечить выполнение инвариантов и предпринимать дополнительных действий при обращении к полю

Если класс доступен за пределами пакета, следует обеспечить методы доступа. Но если класс доступен в пределах пакета или
является закрытым вложенным классом, то никакого ущерба от предоставления доступа к его полям данных не будет.
